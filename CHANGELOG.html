v2.3.0 — 2026-07-15

核心变更

  • claude-* 别名重定向到 GLM:Claude Code 的 sub-agent / auto mode classifier 内部用 claude-opus-4-8 / claude-sonnet-4-6 / claude-haiku-4-5 等 Claude 官方 model 名发请求(不受用户 /model 设置控制)。v2.2.x 时这些别名在 config.json 的 ds.models 里映射到 deepseek-v4-pro,当 ds key 失效(401)时 sub-agent 全部失败。v2.3.0 把 claude-opus-4-8 / claude-opus-4-7 / claude-sonnet-5 / claude-sonnet-4-6 / claude-haiku-4-5 从 ds.models 移到 bd.models,值改为 glm-5.2。sub-agent 直接走 GLM,不再依赖 ds
  • 流式非 200 防御(proxy.js streaming 分支):上游返回非 200(非 429)状态码时,上游响应是裸 JSON 错误体(非 SSE)。旧版把它当 SSE res.write 半行转发,客户端 SSE 解析器等不到 \n\n 终止符 → JSON Parse error: Unexpected EOF。v2.3.0 改为 upRes.resume() 丢弃上游 body,返回自洽的非流式 JSON 错误(upstream_error + 真实状态码 + Content-Length),客户端能看到真实状态码而非畸形 SSE。日志: STREAM ERROR <code> (non-SSE → JSON)

故障修复

  • 修复 API Error: JSON Parse error: Unexpected EOF:根因是 sub-agent 的 claude-opus-4-8 请求经 ds.models 解析到 deepseek-v4-pro,ds key 401 后上游裸 JSON 错误体被流式路径当 SSE 转发,产生畸形 SSE。Claude Code 把错误归到 user-facing model(如 bd,glm5.2)名下显示,造成"GLM 报 EOF"的误判。实测证据:/tmp/proxy-debug.log 中 REQ model=claude-opus-4-8 ... SEND model=deepseek-v4-pro ... STREAM ERROR 401 大量配对,而 bd,glm5.2 请求全是 STREAM DONE。修复后 claude-opus-4-8 → SEND model=glm-5.2 → 200

同步更新

  • config.json / config.example.json:ds.models 删除 3 个 claude-* 别名,bd.models 新增 5 个 claude-* 别名(opus-4-8 / opus-4-7 / sonnet-5 / sonnet-4-6 / haiku-4-5)→ glm-5.2
  • proxy.js 头部版本 v2.2.0 → v2.3.0,STARTED 日志同步
  • SKILL.md 加 v2.3.0 增量说明 + "JSON Parse error: Unexpected EOF" 故障排除段
  • VERSION 2.2.0 → 2.3.0

无破坏性变更:ds / mm provider 接口未变;claude-* 别名改走 GLM 是行为修正(原先走失效的 ds 必然 401)。Router 段未改。

v1.3.2 — 2026-06-09

Fixed

  • 429 风暴导致进程退出根因修复：持续 429 时客户端(Claude)快速断开重试触发 res.write 的 EPIPE，原有代码未监听 req/res/upRes/upstream 的 error 事件，错误冒泡为 uncaughtException 杀掉整个 proxy 进程。新增四层 socket 错误监听 + 进程级 uncaughtException / unhandledRejection 兜底
  • 429 限流降级：收到上游 429 后进入 30s coolDown，期间同 provider 全部请求直接返回 503 + Retry-After。流式 429 必须立刻丢弃上游 body 改写为 503（非透传 429），否则客户端会持续重试让 coolDown 失效
  • coolDown 字典污染修复：shortNameOf 旧版在模型名不含逗号时返回整个字符串，会让同 provider 不同 model 共享不到 coolDown 状态；新版严格校验 PROVIDERS key，否则返回 null 走 unknown 分桶
  • 流式 429 改写：流式分支收到 429 时不再透传 upRes.statusCode，立刻 upRes.resume() 丢弃上游 body 并写 503 + Retry-After，避免 coolDown 窗口形同虚设

Added

  • log rotate：/tmp/proxy-debug.log 超过 5MB 自动 .log → .log.1 轮转，防止长期运行撑爆 /tmp
  • 进程异常保护：process.on('uncaughtException') + process.on('unhandledRejection') 双兜底；日志记录 code + message + stack 前 3 行
  • socket 错误监听：req/res/upRes/upstream 四处全部 .on('error')，日志格式 <LABEL> ERR <code> <message>
  • 日志注入防护：用户传入的 data.model 在写入日志前单行化（替换 \r\n 为空格），防止日志格式注入
  • tests/test-429-backoff-and-rotate.js：8 项 TDD 测试守护 v1.3.2 的 4 项修复，防止静默回归
